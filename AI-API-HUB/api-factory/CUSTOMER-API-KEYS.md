# Product 001 customer API keys

## Scope

This feature separates customer credentials from the internal factory control-plane key. The raw customer key is generated by the Render API Factory, returned once to the administrator, and never stored in the registry or Supabase. Only its SHA-256 digest is stored in `api_factory_customer_keys`.

The gateway's internal `x-factory-key` remains an infrastructure credential. Never provide `FACTORY_API_KEY` to a customer.

## Control-plane routes

All routes below require the internal `x-api-key` control-plane credential.

- `POST /v1/factory/customer-keys` — create a customer key. JSON body: `{"label":"pilot-name","quotaLimit":25}`. The response contains `apiKey` once, plus the key ID and quota metadata. `quotaLimit` must be an integer from 1 to 100000.
- `GET /v1/factory/customer-keys/:id/usage` — inspect quota usage and the latest 20 usage events.
- `POST /v1/factory/customer-keys/:id/revoke` — revoke a key immediately.

Do not log or copy the one-time `apiKey` response into GitHub, repository files, issue comments, or CI logs.

## Customer request

Use the generated `sal31_` key only in the `x-api-key` header when calling:

`POST /v1/factory/research/username`

The internal factory key continues to work for operator smoke tests and does not consume a customer quota. Customer keys are verified and consumed through the durable Supabase gateway. The database transaction locks the key row, checks active status and quota, increments the usage count, and inserts a usage event atomically. Concurrent requests cannot exceed the configured quota.

Quota accounting counts each syntactically valid research request attempt before Sherlock runs. A provider outage or timeout therefore consumes one request from the quota; this is intentional for the initial pilot to bound resource usage and must be stated to customers. Invalid usernames/timeouts are rejected before quota consumption.

## Gateway schema and activation order

The source change is not active merely because it is merged. The following must all be completed and verified:

1. Apply `migrations/20261025_customer_api_keys.sql` to the dedicated `salamou-31-api-factory` Supabase project.
2. Deploy the `api-factory-storage` Edge Function with the customer-key routes while preserving the currently deployed internal-key digest allowlist.
3. Deploy the Render API Factory runtime with `customer-key-store.mjs` and the customer-key routes.
4. Run unit tests and live smoke tests that create a test key, make one successful research request, verify quota rejection, revoke the key, and verify post-revocation rejection.
5. Revoke test keys and confirm no test key is active after the smoke run.

Do not deploy the Render code before the database migration and gateway version are ready: the customer routes fail closed when durable key storage is unavailable.

## Commercial boundary

This implements customer authentication and request quotas, not payment processing. There is no automatic checkout, billing, or revenue evidence in this feature. Start with a small manually invoiced/paid pilot only after a customer key has been issued and independently tested; record revenue only after an actual payment is observed.
